# エージェントが書く文書は、文書だけで通じるように書く

README・仕様書・設計書・手順書・規則・SKILL.md・プロンプトのような文書は、書いたときの
やり取りを知らない人が読む。読み手が文書だけを読んで分かるように書く。

## 文章の種類で経緯の扱いが変わる

| 書くもの | 書くこと | 作業の経緯 |
|---|---|---|
| ユーザーへの返答 | 状況と、ユーザーに決めてもらうことがあれば、決めてもらう内容 | 状況の理解に必要な分だけ、何をしたか・何のためかを書く（規則「ユーザーへの返答は、経緯を追っていない人が読んで分かるように書く」（`writing-to-user.md`）） |
| 文書の本文 | 対象自体 | 書かない。文書だけを読む人に向けて書く |
| コミットメッセージ・PR の本文 | 何を変えたか、なぜ変えたか | 変えた理由は書く。試した順や苦労は書かない |
| コードのコメント | コードが今の形になっている理由 | 書かない。経緯はバージョン管理の履歴に任せる |

どれに当たるか迷ったら、渡したあとに、やり取りを知らない人が文章だけを読むかで決める。
読むなら文書として書く。返答の中に文書の全文を載せるときは、全文の部分を文書として書く。

## 文書の本文の書き方

- 対象自体を語る。文書自身の構成（「本章では」）、作った経緯（「ご指摘を受けて」）、
  指示への応答（「ご依頼の一覧です」）は書かない。
- 文書の外にあるものを前提にしない。会話の中で決めたこと・別の文書・会話の場での合意が要るなら、
  必要な分を本文に書く。
- 語の指す先を、語と一緒に読まれる範囲（節・表の1行・スライドの1枚など）の中に置く。
  読み手は範囲の中だけを拾って読むことがある。指示語（「これ」「その」「こう」のようなこそあど言葉）は
  使わず、指す先の名前を書く。前の状態を指す語（「もう」「すでに」）は、状態自体を書く。
  「何の」「誰の」が無い一般語と、何と比べたかの無い「だけ」も、何の・誰の・何と比べてかを書く。
- 書き手が作った呼び名を説明なしに続けて使わない。「戦略的」「最適化」のように中身が
  決まらない語で済ませず、何をどうするかを書く。
- 動く人を文に残す。誰が何をするかを受け身や名詞の並びで消さない。
- 数には確かさを添える。測った値か見積もりか、何を含まないかを書く。
- スキル・規則・プロンプトのように、エージェントが読んで動く文書は、
  「エージェント向けの指示文の書き方」（`writing-instructions.md`）にも沿う。
  セッションに読み込まれていなければ、wakariyasu のスキルのフォルダにある `references/writing-instructions.md` を読む。
- リポジトリの最上位に置き、ツールを外部に公開する README（ツールが何であり、どうセットアップすれば使えるかを
  伝える文書）を書く・直すときは、「README の書き方」（`readme.md`）にも沿う。
  セッションに読み込まれていなければ、wakariyasu のスキルのフォルダにある `references/readme.md` を読む。

## 書き終えたら

次の順で仕上げる。

1. `remove-meta-narrative` スキルで、作業の経緯や文書自身を語る文を探して直す。
2. 人に渡す・公開する文書は、`review-for-readers` スキルで、経緯を知らない読み手の目で読み直す。
3. 規則「書いた文章は、渡す前に整える」（`polishing.md`）に沿って自分で整える。
   セッションに読み込まれていなければ、wakariyasu のスキルのフォルダにある `references/polishing.md` を読む。
4. 人に渡す日本語の文書は、使えるスキルの中に yomiyasu があれば、yomiyasu スキルを呼び出し、
   文書と文章の種類を渡す。

手順 2 の `review-for-readers` は、手順 3 と 4 を中で済ませる。済ませたなら、もう一度しなくてよい。
