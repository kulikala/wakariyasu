# 読み手の視点で読み直す

文書を書いた側は書いたときのやり取りを覚えているので、文書に書いていないことまで読めてしまう。
経緯を知らない読み手に文書だけを読ませ、読み手が引っかかる箇所を直す。

## 1. 読み手を用意する

経緯を渡さない別のエージェント（サブエージェント）を起こし、次の2つだけを渡す。

- 文書の本文（ファイルのパスか、全文）。
- 想定する読み手を1行で（例：「ツールを初めて知った開発者」「業務を知らない社内の担当者」）。

作業の経緯・書いた意図・直した箇所は渡さない。渡すと、読み手は書き手と同じものが読めてしまう。
読み手には渡した文書以外のファイル（同じリポジトリの指示のファイルなど）を開かないように頼む。

別のエージェントを起こせない環境では、自分で文書だけを頭から1回読み直し、「2. 読み手に頼むこと」の節の観点で
直す。書き手は前のバージョンを覚えているので、書き手が何度読み直しても読み手の代わりにはならない。「3. 直して、もう一度読ませる」の節の、別の読み手にもう一度読ませる手順は省く。報告に
「別の読み手ではなく、書き手が読み直した」と書く。

## 2. 読み手に頼むこと

読み手には文書を頭から順に読み、前に戻らずに読んでもらう。読んだうえで、次に当たる箇所を、
場所と理由を添えて挙げてもらう。直し方の案は求めない。

- 意味が決まらない語。作った呼び名、説明のない略称、「戦略的」のように中身の決まらない語。
- 示す対象が分からない語。指示語（「これ」「それ」）や、「何の」「誰の」が無い一般語。
- 文書に書かれていない前提が必要な文。会話の中で決めたこと、別の文書の中身。
- 前に戻って読み直した箇所。戻った理由も。
- 読み終えて、答えの出ない疑問。「結局、何ができるのか」「自分は何をすればよいのか」。

日本語の文書なら、迷った文を英語に直訳させる。主語・目的語・冠詞を補わないと英文にならないなら、
元の日本語の文は示す対象が足りない。

## 3. 直して、もう一度読ませる

挙がった箇所を直す。直すときは、規則「エージェントが書く文書は、文書だけで通じるように書く」（`writing-documents.md`）に沿う。セッションに読み込まれていなければ、review-for-readers スキルのフォルダにある `references/writing-documents.md` を読む。
作った経緯や文書自身を語る文が見つかったら、
`remove-meta-narrative` スキルで直す。最後に、規則「書いた文章は、渡す前に整える」（`polishing.md`）に
沿って整える。セッションに読み込まれていなければ、review-for-readers スキルのフォルダにある `references/polishing.md` を読む。

直したら、前とは別の、経緯を知らない読み手にもう一度読ませる。同じ読み手は前のバージョンを覚えている。
読み手が理解を妨げる箇所を挙げなくなるまで繰り返す。目安は2〜3回。

日本語の文書で、読み手が挙げなくなったら、使えるスキルの中に yomiyasu があれば yomiyasu スキルを呼び出し、文書と
文章の種類を渡して整える。種類は README・技術記事なら article、手順書なら manual、規則・仕様書なら formal のような名前で、「日本語の表記の選び方」（`styles.md`）の表の「種類」の列にある。セッションに読み込まれていなければ、review-for-readers スキルのフォルダにある `references/styles.md` を読む。

## 4. 報告する

- 何回読ませたか、読み手がどの観点で読んだか。
- 挙がった箇所と、どう直したか。直さなかった箇所は直さなかった理由。
- 確かめていないこと（例：英語版は読ませていない、実際の手順は動かしていない）。
