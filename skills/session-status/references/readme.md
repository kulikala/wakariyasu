# README の書き方

README はツールを試すか決める人、インストールする人、使い始める人が最初に開く文書だ。読み手は章の名前を
手がかりに、必要な所へ飛ぶ。日本語の README は、人が手で保守している日本語の README と同じ章の名前・
組み立て・言葉で書き、読み手が見慣れた形の中で探すものを見つけられるようにする。手本にするのは、
同じ分野で、人が手で日本語の README を保守しているツールだ。ファイルやウェブを読めるなら、手本を
いくつか開いて確かめる。読めないなら、この書き方に挙げた章の名前を使う。リポジトリに README の書き方を
決めた文書があれば、そちらを先に読んで従い、その文書が決めていない点にこの書き方を当てる。

## 章の組み立て

章は次の順に置く。ツールに当てはまらない章（ダウンロードするモデルの無いツールの容量の章など）は立てない。

1. ツールの説明と出力の例
2. 機能（機能の区分が2つ以上あるとき）
3. 特長
4. 向いている用途
5. 免責事項
6. 対応環境
7. 必要なディスク容量
8. 別途必要なソフトウェア
9. インストール
10. 使い方
11. ツールに固有の章（エージェント・スキル、精度など）
12. 開発者ガイド
13. ライセンス

各章の書き方は次のとおり。

- 機能に区分があるなら、区分の一覧を、区分の名前が初めて出る章より前に置く。区分は、利用者が別々に
  使える機能のまとまり（別のコマンド、別のモードなど）を指す。機能がいくつの区分に分かれ、それぞれが
  何をするかを、「機能区分」「コマンド」「説明」の表で示す。区分の名前を説明する前に使うと、読み手は
  以降の表や節についていけない。区分が1つだけなら、表は立てずに冒頭の説明で足りる。
- 向いている用途の章には向く用途と向かない用途だけを書く。向かない用途の項目に、別の使い方で
  できること（「ただし〜のオプションで文字起こしできます」）を混ぜない。できることは使い方の章に書き、
  向いている用途の章からはそこへリンクする。向かない用途は、ツールが受け持つ作業の中で向かないものに限る。
- ツールの前後で利用者が行う作業（ツールに渡す録音を用意する、ツールの出力を要約するなど）は、向かない用途に
  入れず、免責事項の章に、ツールが受け持つ範囲として書く。前後の作業を向かない用途に並べると、ツールを使う流れの
  一部が、ツールに合わない使い方のように読める。結果に誤りが残るツールなら、結果をどう扱うかも免責事項に書く。
- 対応環境は対応表で書く。読み手は自分の PC で何が動くかを知りたいので、OS ごとに、機能の区分が使えるか、
  CPU と GPU のどちらで動くかのように、自分の環境に当てはめられる表にする。GPU を使わないツールなら、
  CPU・GPU の代わりに「対応」「非対応」を書く。対応していない OS も表の行にして「非対応」と書き、
  表の外に「〜には対応していません」と文で書かない。どこまで試したかのような作業の記録は書かない。
  README は作業の報告書ではない。
- ダウンロードするモデルやデータが大きいなら、必要なディスク容量を独立した章にする。列は「機能区分」
  「ダウンロードするモデル」「用途」「容量」とし、そのモデルが何のために使われるかを用途の列に書く。
  読み手は使う機能区分の行を足せば、必要な容量が分かる。モデルでなくデータをダウンロードするなら、
  2つ目の列は「ダウンロードするデータ」とする。
- ツールに含まれず、利用者が各自でインストールするソフトウェアは、「別途必要なソフトウェア」の章に
  まとめ、各自でインストールするよう案内する。列は「ソフトウェア」「バージョン」「要否」「説明」とする。
  バージョンの列には使える最も古いバージョン（「0.40.0 以上」）を書き、決まりが無ければ「指定なし」と書く。
  要否の列には必須か任意かを書き、任意なら、どんな場面で必要になるかを添える。インストールの章を含む
  ほかの章では、ソフトウェアを利用者が自分でインストールすることを地の文で述べず、この章へリンクする。
- インストールの章は OS ごとの節（「macOS の場合」「Linux の場合」「Windows の場合」）に分け、
  どこで（ターミナル、PowerShell など）何を実行するかだけを書く。インストールのオプション（環境変数など）を
  使うコマンドも、その OS の節に書いてよい。インストールスクリプトの中の動き、対応環境、容量、別途必要な
  ソフトウェア、使い方は、それぞれの章に置く。対応していない OS は対応環境の表に書き、インストールの章で
  「〜では動きません」と案内しない。
- 章の名前は、人が手で保守している日本語の README で使われている名前に合わせる。英語の見出しを直訳した
  名前（Development を「開発」）は、日本語の README では見かけない。開発に参加する人向けの章は
  「開発者ガイド」、AI エージェント向けのスキルの章は「エージェント・スキル」とする。
- 保守していない旧版を使う案内は書かない。旧版があり、そこから移る利用者がいるなら、移るときの手順だけを、
  インストールの詳しい文書（README から分けているなら、その文書）に書く。

## 言葉

- 人が書く日本語の技術文書では見かけない言い回しは、見かける言い回しに替える。翻訳調の言い回しは
  読み手に文書を信頼しにくくさせる。迷ったら、その言い回しを人が手で保守している日本語の技術文書で見かけるかで
  決める。言い換えの例は次のとおり。
  - コマンドを「打つ」は「実行する」。
  - 「旗」は「オプション」。
  - 「導入」は「インストール」か「セットアップ」。
  - 「要る」は「必要な」「必要です」。「別にインストールする」の「別に」は「別途」。
  - 作業の一覧の見出しの「やること」は「対応内容」。
  - 表の列の「使う機能」「取得するもの」は「機能区分」「ダウンロードするモデル」。
- 「端末」は PC やスマートフォンのような機器を指す。コマンドを実行するアプリは「ターミナル」と書く。
- 書き手が作った呼び名は、ツールの外では通じないので使わない。まとめて渡すデータを「束」と呼ぶような造語は、
  中身を表す一般の語に替える。ツールのコマンドや出力が使う語（機能の名前など）は、利用者が画面で見比べるので
  そのまま使い、初めて出る所で意味を添える。造語を替えるときは、替えた語を英語に直して、指すものの
  中身と合うかを確かめる。
  LLM に渡す指示と依頼をまとめた JSON を「問い」と呼ぶと、英語では question になり中身と合わない。
  中身に合う「プロンプト」を使い、「プロンプトの JSON」と呼ぶ。

## 仕上げ

書き終えたら、規則 `writing-documents` の「書き終えたら」の順で仕上げる。yomiyasu を使えるなら、
文書の種類として `article`（技術記事・README）を渡す。
